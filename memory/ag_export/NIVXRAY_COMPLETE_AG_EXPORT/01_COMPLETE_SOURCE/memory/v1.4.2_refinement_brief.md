# v1.4.2 · Refinement Brief — Evidence vs Interpretation Discipline

**Recorded:** 2026-07-27 (SME review of shipped v1.4.1)
**Rating from reviewer:** v1.4.1 = 9.5 / 10 · architecture correct, remaining work is hygiene
**Severity:** P1 (correctness refinement · not blocking)

---

## Principle to lock in
Separate **observed behaviour** from **ATT&CK interpretation** in
every emitted node, every rationale, and every UI panel. The
Behaviour Graph carries the *what*; the MITRE mapping carries the
*how it maps to the tactic*. The two must never be conflated.

```
Observed behaviour              ATT&CK interpretation
────────────────────            ─────────────────────
Firewall rule modification  ─►  Defense Evasion (T1562.004)
WinRM configuration         ─►  Lateral Movement enablement (T1021.006)
Credentialed remote exec    ─►  Remote Services (T1021.002)
```

## Three refinements for v1.4.2

### R-1 · Behaviour naming should describe *what happened*, not *the tactic*

**Problem** — `Enable-NetFirewallRule` is currently emitted as
`DEFENSE_EVASION`. In many contexts it is just an admin
configuration change. Firing the tactic label at the *behaviour*
layer conflates observation with interpretation.

**Fix** — rename the internal behaviour to observation-form and
attach the tactic as a MITRE tag on the node:

| Current                 | v1.4.2                          | ATT&CK tag |
| ----------------------- | ------------------------------- | ---------- |
| `DEFENSE_EVASION` node from firewall rule | `firewall_configuration` behaviour node | `T1562.004` on the node |
| `DEFENSE_EVASION` from AMSI/ETW patch     | `defense_tampering` node                 | `T1562.001` on the node |

Where possible, keep the observation-form kind small and tag ATT&CK
on the node. The Verdict Engine can still reason
`firewall_configuration ∧ remote_management_enablement ⇒ MALICIOUS`
using the *composition* — the interpretation happens at scoring
time, not naming time.

Fallback if a schema-name change is too expensive: keep the enum
name `defense_evasion` but change every `purpose` / `rationale`
string to describe the *observation* ("Modifies Windows Firewall
rules to permit remote-management traffic") and put the tactic
label only in the MITRE tags. This is the cheaper interim fix.

### R-2 · Prune MITRE mappings to evidence-supported hits only

**Reviewer flagged** two mappings on the T15 sample that need
re-checking against the actual command:

| MITRE ID | Current source          | Reviewer concern                                            | Action |
| -------- | ----------------------- | ----------------------------------------------------------- | ------ |
| `T1552.001` (Credentials in Files) | Emitted when `-p <password>` appears | T1552.001 = *credentials discovered in files*, not *passwords passed on cmdline*. Better mapping: `T1078.002` (Valid Accounts · Domain) or leave uncited. | **Remove** T1552.001 from `PsExecCredentialedRule`. Keep `T1078` (Valid Accounts). If we want to flag cmdline credential exposure at all, use `T1552` parent OR emit no ID and cite it only in the rationale. |
| `T1548` (Abuse Elevation Control) | Emitted when PsExec `-h` / `-s` seen | `-h` requests an elevated token — technically an elevation *request*, not an abuse *of a control mechanism*. Legit admins also use `-h`. | **Remove** T1548 from the default emission. Cite the elevation observation in the Evidence rationale only. Add T1548 back only if we find a corroborating abuse pattern (UAC bypass, token duplication). |

Every remaining MITRE ID must have a **direct one-line evidence
citation** in the Intent's Evidence list. If the citation reads
awkwardly ("we tag this because we always do"), remove the ID.

### R-3 · Verdict must self-explain the composition

**Problem** — the current reason string:
```
High-risk adversarial intent chain detected: lateral_movement + defense_evasion.
Behaviour is consistent with malicious execution.
```
is correct but doesn't show *what was observed* or *why the
composition matters*.

**Target output shape**:
```
Verdict: MALICIOUS (90)

Reasoning
─────────
Observed:
  ✓ PsExec remote execution
  ✓ Explicit credentials passed on command line
  ✓ WinRM / PSRemoting enablement
  ✓ Firewall rule modification (remote-management channel opened)

Behaviour Composition:
  Remote Execution + Credentialed Administration + Remote Management Enablement

Conclusion:
  High-confidence malicious operational sequence.
  Legitimate administration cannot be ruled out from the artefact
  alone — verify against approved change tickets.
```

Implementation:

- Add a `Verdict.reasoning` field (structured):
  ```
  reasoning: {
    observed:    list[str]   # one line per fired intent's purpose (observation-form)
    composition: list[str]   # the categories used by the scoring rule
    conclusion:  str         # the analyst-facing sentence
    ambiguity:   str         # the honesty caveat for dual-use compositions
  }
  ```
- Populate `observed` from the fired `Intent.purpose` sentences.
- Populate `composition` from the categories that triggered the
  verdict rule (e.g. `["LATERAL_MOVEMENT", "DEFENSE_EVASION"]`).
- Populate `conclusion` from the existing `reason` string.
- Populate `ambiguity` deterministically for dual-use rules
  (LATERAL_MOVEMENT-based verdicts, credentialed-admin patterns).
- Keep the flat `reason` string for backward compatibility.
- Analyst Report + Investigation Brain UI render the four
  subsections instead of the single reason line.

## Acceptance criteria for v1.4.2

1. T15 verdict output includes an `Observed / Composition / Conclusion / Ambiguity` block, rendered in the UI.
2. No MITRE ID appears without a matching one-line evidence citation.
3. `T1552.001` and `T1548` are removed from `PsExecCredentialedRule` (or replaced with better-fit IDs after review).
4. Behaviour node names are observation-form; ATT&CK labels are tags only.
5. All 331/331 tests remain green; T15 corpus stays 15/15 with adjusted `expected_mitre` list.
6. Determinism preserved — the new `reasoning` block hashes into `determinism_hash`.
7. No new engines, no schema-version bump required (this is a refinement inside the frozen `1.1.0` contract).

- No changes to IU / CRE / RTE.
- No PDF export, no correlation, no static control flow.
- The Analyst Summary legacy UI panel remains a separate ticket (FU-5).
