01 · POSITIONING

What NivXRay is (and isn't)

NivXRay is NOT a SIEM. NivXRay is NOT an EDR.
NivXRay is a Deep-Decode + MITRE-Attribution + IOC-Enrichment micro-service that plugs into an existing SOC stack in one of two ways — Type-I (inline / automatic) or Type-II (on-demand / analyst-triggered).

One-line pitch

"Turn every obfuscated command your EDR shipped into a MITRE-tagged verdict in <200 ms — without touching your SIEM schema."

What NivXRay does that your stack doesn't

02 · TYPE-I.A · PARALLEL SIDECAR

Type-I.A · Parallel sidecar (NivXRay writes to SIEM directly)

NivXRay pulls logs from EDR, decodes autonomously, then writes BOTH the original EDR data AND the NivXRay-enriched analysis into SIEM/XDR/ServiceNow as a single combined event.

How it works

  • NivXRay reads EDR events via EDR's API / event stream
  • Decodes autonomously — zero human intervention
  • Writes BOTH the original EDR event AND NivXRay's decoded output to SIEM as one combined record
  • Analyst opens SIEM notable — sees EDR fields + nivxray.verdict, nivxray.mitre[], nivxray.ti_hits[] already populated

Trade-offs

  • ✅ Zero EDR impact — EDR pipeline untouched
  • ✅ NivXRay failure ≠ EDR failure (fault-isolated)
  • ✅ Faster to deploy (no EDR change window)
  • ⚠️ Duplicate ingest to SIEM (EDR row + NivXRay row → correlate on source_alert_id)
  • ⚠️ Two writes to SIEM per event → SIEM licensing implication
03 · TYPE-I.B · ENRICH-BACK-TO-EDR

Type-I.B · Enrich-back-to-EDR (single alert, combined data)

NivXRay pulls logs from EDR, decodes, sends the enriched output BACK to EDR. EDR fires the alert (with combined EDR + NivXRay data) into SIEM/XDR/ServiceNow — one single, richer alert per event.

How it works

  • NivXRay reads EDR events (same as I.A)
  • Decodes autonomously
  • Sends output back to EDR via EDR's custom-field / IOA-tag API
  • EDR fires ONE enriched alert into SIEM — no duplicate rows
  • Analyst opens SIEM notable — everything is on a single record

Trade-offs

  • ✅ Single alert per event — clean triage view
  • ✅ No SIEM licensing doubling
  • ✅ Preserves EDR as source of truth
  • ⚠️ Requires EDR support for writable custom fields (CrowdStrike Fusion / SentinelOne STAR / Defender custom detections)
  • ⚠️ Slight latency (EDR waits ~200 ms for NivXRay before firing)
04 · TYPE-II · ON-DEMAND ANALYST

Type-II · On-demand analyst investigation

Completely end-user driven. After a new alert lands in SIEM/XDR/ServiceNow, the analyst manually pulls the suspicious payload into NivXRay for deep investigation. NivXRay is NOT in the automatic pipeline.

How it works

  • SIEM/XDR fires a new alert normally
  • Analyst investigates in SIEM — spots a suspicious commandline/payload
  • Analyst opens NivXRay Workspace and pastes the payload
  • Deep-decode returns MITRE + LOLBAS + IOCs + TI-HITS + AI narrative
  • Analyst uses NivXRay's findings to close/escalate the alert in SIEM

Trade-offs

  • ✅ Zero SIEM/EDR change — plug in on day one
  • ✅ No pipeline risk — NivXRay outage doesn't affect detection
  • ✅ Best POC path (2-week eval, no engineering cost)
  • ⚠️ Depends on analyst discipline (they must choose to pull)
  • ⚠️ Doesn't scale to high alert volumes
Recommended adoption path: Type-II (2-week POC · zero risk) → Type-I.A (parallel sidecar · quick production) → Type-I.B (enrich-back-to-EDR · full clean integration).

Security architecture

  • Auth: JWT bearer · per-tenant issuer · rotation every 24h
  • Rate limit: 100 req/sec per tenant · login endpoint hardened separately (P0)
  • Payload cap: 20KB per request · 500 per batch
  • Egress: outbound VT/OTX/AbuseIPDB via allow-listed proxy
  • Secrets: AWS Secrets Manager / GCP Secret Manager / K8s sealed-secrets
  • Audit: every decode → X-Request-ID → Mongo + stdout
  • PII policy: no raw payload stored unless retain_payload=true
  • Data residency: US · EU · APAC (per-tenant pinning)
