## ASSESSMENT — authoritative production store vs test binding

- The database name contains the token `test_database` **only because the preview `DB_NAME` was `test_database`** and the platform namespaced it to the app slug at first secret-seed. The `test` substring is cosmetic/inherited, not evidence of a staging binding.
- Within this deployment the binding is **stable and singular**: every run (2026-10-03 → 2026-10-15) binds exactly `greeting-app-5782-test_database`, the code uses a single `deps.db`, and that DB holds large, real operational history including the owner's own endpoint with 157,226 telemetry events. **Production traffic has consistently and exclusively landed in this database.** By the evidence available, this IS the store production uses and has always used — not a stray test binding that only recently started receiving traffic.
- **What CANNOT be certified with available tooling, and must not be inferred:** (a) that no *other, better-populated* EDR database exists elsewhere on the same MongoDB cluster, and (b) the cluster host/identity behind `MONGO_URL`. Both require the owner to inspect MongoDB Atlas directly (listDatabases + the live connection target). Until that external check is done, the statement "this is the single authoritative cluster-wide store" rests on an un-enumerable cluster and is therefore **not fully certifiable from inside the deployment** — this limitation is itself a reportable finding.

**Net:** For the purpose of the re-enrolment decision — within this deployment this is unambiguously the one store production reads and writes, and it holds genuine history (including the subject endpoint). The only residual uncertainty is cluster-level (is there a *different* DB that *should* have been used), which only Atlas access can close.
