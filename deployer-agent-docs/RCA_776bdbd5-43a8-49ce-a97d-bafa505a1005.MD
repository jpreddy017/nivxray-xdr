## ROOT_CAUSE
The `password` field on the live admin document does **not** contain a bcrypt hash — it contains a short **plaintext-style, non-bcrypt string** (12 chars, no `$2b$12$` prefix, BSON string). The login path is correct and unchanged: it calls `bcrypt.checkpw(entered_password, stored_value)`. Because `stored_value` is not a valid bcrypt hash, `checkpw` raises "invalid salt", which `verify_password` swallows and returns `False` → **401 for every attempt, with any password**, because there is no valid hash to verify against. The 6ms response on the latest attempt (vs ~331–524ms when a real hash was present earlier) is the decisive proof that bcrypt never performed real verification work after the 20:14:16 edit.

In short: whatever was placed into the `password` field during the reset was **not** the `$2b$12$…` 60-char hash the owner intended — the field now holds a plaintext-length string. The DB Manager stores the field verbatim; it does not hash on save. So the stored value must itself already be a bcrypt hash, and currently it is not.
