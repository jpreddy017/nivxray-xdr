**Verdict:** The v1.5.6 offload IS live. The 524 is NOT stale code — it is **CPU starvation on tier_0**, made worse by a **soft-cancel flaw** in the offload (abandoned decoder threads keep burning CPU after the 504). The required tier_0→tier_1+ upgrade was NOT done.

### 1. What version is RUNNING? → v1.5.6 offload IS live (NOT v1.5.5b).
The offload code path is unambiguously executing in the current pod. Log evidence:
- `02:48:22 WARNING decode_timeout fn=deterministic_best_decode timeout_s=25.0 args_len=7624`
- `02:48:22 WARNING [nvx-413f67f7dedd] slow path=/api/decode/smart elapsed_ms=25414 status=504`

That is exactly the `decode_offload.py` behavior: a 25s wall-clock budget via `asyncio.wait_for` raising `HTTPException(504, code=decode_timeout)`. v1.5.5b or older would have silently stalled ~21s with NO `decode_timeout` warning and NO 504. **So no rebuild is needed to get the offload live — it already is.** (v1.5.7 was UI-only, indistinguishable at the backend; the backend is 1.5.6-class.)

## Why a 524 at 30–40s (not a clean 504, and not Cloudflare's 100s ceiling)

The app *decides* to return 504 at 25s — but the user still sees a Cloudflare **524**. Two compounding causes:

1. **Soft cancel in the offload.** `asyncio.wait_for(run_in_executor(...))` cancels the *awaiting coroutine* at 25s, but it **cannot kill the underlying OS thread** running the synchronous `xor-brute`. The abandoned thread keeps burning CPU for another 27–35s (see the `slow decoder xor-brute: 35382ms/27443ms` lines logged AFTER the 504). Overlapping requests stack multiple zombie threads (two decode_timeout events 53s apart).
2. **0.25-core cap (tier_0).** With `uvicorn --workers 1` and these zombie threads pegging a quarter-core, the event loop is starved — it can't promptly serialize/flush even the 504 response, and can't answer `/health` within nginx's 1s window (hence the probe 503s). To the Cloudflare edge the origin looks hung → the edge tears down the half-open connection → **524**.

**Ruled out — the user's alternate hypotheses:**
- **nginx `proxy_read_timeout` too short:** NO. There is no nginx.conf override in GCS (`get_deployment_manifest` → not_found), so the build uses the farm default where `location /api` has `proxy_read_timeout 86400`. The k8s-side nginx is not truncating at 30–40s.
- **Cloudflare 100s ceiling being hit:** NO. 30–40s is well under 100s; the 524 is the edge giving up on a *stalled/half-open* origin under starvation, not the max-timeout ceiling.

So the 30–40s the user observed = "504 decided at 25s" + extra seconds where the starved event loop fails to flush the response while zombie decoder threads saturate the CPU.

---

## Root cause (one line)
The offload fix is deployed, but (a) the pod is still on **tier_0 (0.25-core)** and (b) the offload only *soft-cancels* — timed-out `xor-brute` threads keep consuming CPU after the 504, starving the single-worker event loop so the 504 can't be flushed → Cloudflare 524.

## Remediation
**Immediate (user, UI — no redeploy needed):** Deployment Panel → Resources → upgrade **tier_0 → tier_1+**. More CPU lets the event loop flush the 504 promptly (user sees a clean 504 `code=decode_timeout` instead of a 524) and reduces starvation-driven probe 503s. This alone likely clears the 524.

**Source-side (E1, for a future deploy — the durable fix):** the `wait_for` + `run_in_executor` pattern cannot kill a runaway sync thread. Options:
- Run heavy decoders (`xor-brute`, L3, `magic_decode`, `recipe.run`, `analyze/shellcode`) in a **ProcessPoolExecutor** so a timed-out job can actually be terminated (frees CPU at the 25s boundary instead of letting it run 35s).
- Add a **hard input-size / iteration cap** for `xor-brute` (845B triggering a 35s brute-force is the adversarial class) and/or a cooperative cancellation check.
- Keep the 25s budget BELOW the edge/proxy limits, but the key is that the timed-out work must actually STOP, not just be abandoned. Do NOT simply raise the 25s budget — on constrained CPU it makes the stall longer, not shorter.

**Note on "force a rebuild against feature/rc2.1b HEAD":** not required for the offload (it's already live). If you want to ship the ProcessPool/input-cap fix, land it in the preview/source environment and deploy normally — the deploy pipeline pulls from the source env, it does not build an arbitrary git ref on demand.
