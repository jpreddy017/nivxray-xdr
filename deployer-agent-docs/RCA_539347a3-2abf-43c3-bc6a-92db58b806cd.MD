# RCA — NivXRay (greeting-app-5782) Cloudflare 520 on nivxray.nivxforge.com

## Verdict
The v1.5.5b redeploy (run `539347a3-2abf-43c3-bc6a-92db58b806cd`) **succeeded and was promoted** — it is the current active run. The Cloudflare 520 is a **runtime origin failure caused by CPU starvation on tier_0**, NOT a build failure, NOT the frontend-only patch, NOT an env/secret change. A rollback to v1.5.5 would NOT fix it (same decode code, same tier, same starvation).

## What each investigation point showed
1. **Pipeline** — `539347a3` status=success, promoted (active_run_id points to it). No mid-build crash. Build was skipped/reused appropriately; deploy + health_check + promote all green.
2. **Backend pod** — boots cleanly: `Application startup complete`, `Uvicorn running on http://0.0.0.0:8001`, `Decoder registry ready — 61 plugins loaded`. NOT an OOM (last termination = exit 0 "Completed" from a liveness kill, not exit 137). One restart (restart_count=1) then recovered to Running/Ready.
3. **Frontend build/serve** — healthy. Edge serves the SPA `index.html` (200). Static build present. No empty-response from the frontend path.
4. **Port binding** — correct. Backend on 8001, nginx fronts 8080 (the port Cloudflare's origin expects). Container port 8080/TCP. No misbinding.
5. **Env/secrets** — no relevant change; frontend-only patch. Only external anomaly is a benign `threatfox 401 Unauthorized` (3rd-party TI feed), unrelated to the 520.

## Root cause (evidence-backed)
The backend runs CPU-bound decode work **synchronously on the asyncio event loop**, and under tier_0's **250m CPU cap (0.25 vCPU)** a single heavy decode monopolizes the quota and blocks the loop for tens of seconds:
- `slow decoder xor-brute: 21500ms on 845B input` (and 17891ms)
- `L3: dispatch failed: TimeoutError('L3 dispatch exceeded hard_timeout=13.0s')` (repeated)
- `slow path=/health elapsed_ms=18616 status=404` — /health took 18.6s to answer
- `504 server_timeout path=/api/decode/guidance timeout_ms=30000 elapsed_ms=40408`

The nginx `/health` location uses aggressive 1s proxy timeouts and maps upstream 502/503/504 → `@health_error` (returns 503). When the event loop is blocked, /health can't answer within 1s → nginx returns **503** → the k8s liveness/readiness probes fail (observed: `Liveness/Readiness/Startup probe failed: statuscode 503`, count 8–9) → after the failure threshold the container is **Killed and restarted** (`failed liveness probe, will be restarted`). Because entrypoint.sh tears down BOTH backend and nginx when either dies, the origin at :8080 goes fully down for that pod during the restart window → Cloudflare gets an empty/reset response it can't parse → **520**.

So the 520 is intermittent: it appears whenever a heavy decode blocks the loop long enough to trip liveness and cycle the container.

## Why it looked correlated with the redeploy
Pure timing. The redeploy restarted the pods right as decode traffic (DECODE / AUTO INVESTIGATE) was hitting the origin, so the CPU-starvation flapping surfaced immediately after the click. Preview looks fine because preview isn't under the tier_0 CPU cap.

## Remediation (in priority order)
1. **Upgrade the deployment tier** (Deployment Panel → Resources) from tier_0 (Starter, 250m CPU) to **tier_1 (Launch) or higher**. This is the direct fix for the event-loop starvation and the fastest path to stop the 520s. (UI action — the deployer agent has no tier-change tool.)
2. **Source mitigation (recommended regardless of tier):** move CPU-bound decoders (xor-brute and the L3 dispatch path) OFF the event loop — run them in a `run_in_executor` / ProcessPool with a hard wall-clock budget — so long decodes never block `/health`. This makes liveness robust even under load.
3. **Optional probe hardening:** decouple the k8s `/health` liveness from the blocked event loop (a lightweight liveness route that doesn't share the decode loop), and/or raise the nginx `/health` proxy timeout above 1s and the probe timeout above 2s. This prevents a slow decode from ever killing the container.

## Not recommended
- A rollback to v1.5.5 or a plain redeploy — the fault is resource/workload, not code regression; it will recur.
