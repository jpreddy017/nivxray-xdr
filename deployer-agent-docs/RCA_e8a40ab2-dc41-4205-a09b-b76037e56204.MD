## 8. Anything that would impede an in-process asyncio background supervisor
- **Scale-to-zero / idle eviction: NO.** Replicas are pinned at 2, HPA disabled, no scale-to-zero. Pods are **kept warm** — one has been up since 2026-09-30T16:11Z, the other since 18:52Z, both restart_count 0. No eviction/OOM events observed.
- **Read-only filesystem: not observed.** The app actively writes (FileStore retention sweeper armed, decoded artifact store, GridFS `*.files/*.chunks`), so the FS is writable.
- **Resources:** tier_3 — CPU request 1 / limit 2, memory 4Gi / limit 8Gi, ephemeral 10Gi. Headroom exists, BUT each replica has only **one uvicorn worker = one event loop**.
- **KEY RISK — liveness/readiness probes vs a single event loop.** Production already shows intermittent health failures:
  - `Readiness probe failed: HTTP ... 503` (×8, last seen 2026-10-01T13:45Z) and `Liveness probe failed: HTTP ... 503` (×6) on pod `...-j2hzk`.
  - nginx: `upstream timed out (110) while reading response header from upstream http://127.0.0.1:8001/health` recurring. The farm `/health` location uses a **1s** proxy timeout.
  - Interpretation: the single event loop is **already intermittently saturated/blocked**, so `/health` occasionally doesn't answer within 1s. A new in-process supervisor that does **blocking or CPU-bound work on the same loop** would increase these 503s. If liveness 503s cross the K8s failureThreshold, **K8s will restart the pod and kill the supervisor mid-task.** (So far restart_count is 0 — the probes have been tolerated, not fatal — but the margin is already thin.)
  - Mitigation to weigh before the new branch: run background work off the request loop (`run_in_executor`/thread/process or an external worker), keep `/health` non-blocking, and ensure graceful SIGTERM handling (entrypoint sends SIGTERM to the backend on rollout — the supervisor must drain/cancel tasks cleanly).
- **Request-timeout killer:** `/api` uses `proxy_read_timeout 86400` (effectively no cap for API calls); only `/health` is on the 1s timeout. Background asyncio tasks are not request-scoped, so nginx request timeouts won't kill them directly — but a blocked loop makes `/health` fail, which is the real lever (see above).
- **Double-run:** with 2 replicas the supervisor runs twice (see #4) — coordinate singletons.
