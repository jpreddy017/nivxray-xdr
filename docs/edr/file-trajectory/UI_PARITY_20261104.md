# EDR File Trajectory UI coverage

Reference: Cisco Secure Endpoint Best Practices Guide, File Trajectory section:
https://www.cisco.com/c/en/us/products/collateral/security/fireamp-endpoints/secure-endpoint-og.html

This change extends PR 56. NivXForge branding and console theme remain. XDR is unchanged by this follow-up.

## Implemented

- Visibility: loaded event and computer counts, first/last loaded times.
- Entry Point section: earliest loaded computer/path, with origin explicitly unestablished.
- Related Processes: source-stated images, expandable per-computer process list, Device Trajectory pivot.
- Collapsible File Details: source-provided hashes, names, sizes, signers and sources.
- Collapsible Network Profile: destination IP, port, protocol, DNS/URL and evidence records correlated by file SHA-256 to process-image SHA-256 and source process GUID, within the same authorized endpoint. Source-stated executable and parent images are shown separately from file writer images.
- Multi-computer SHA-256 search across the computer list returned by the directory API. Each computer is queried through the existing endpoint authorization boundary. Four bounded scans per user interaction; independent continuation cursor per computer. This is not an indexed fleet query or a claim of complete directory coverage.
- Computer-by-time timeline, event icons with expandable density clusters, event legend, zoom/pan/reset, selected-event details, keyboard-accessible controls.
- Event History: chronology toggle, loaded-event search, event-type filter, row pagination, continuation scan and details.
- Refresh, copy investigation URL, JSON export of filtered loaded observations.
- Light/dark console theme tokens and responsive sections; wide timeline scrolls within its panel.

## Data and action gaps — full functional parity is not claimed

The current API does not supply verified file-entry causality, PE/type/version/certificate attributes beyond signer, or detection verdicts. These remain unavailable. No network activity, parent-child edge, clean verdict, file type or origin is fabricated from names or earliest timestamps.

Cisco's file retrieval, application allow/block actions and sandbox submission require authorized product-specific service endpoints. Those actions are not implemented here and no no-op action controls are shown. Crucible is the product sandbox name; no Cisco service is integrated.

No writes to sensor data, response actions, collection migrations, or production deployment occur in this change.

## Bounded network context follow-up

Each authorized file page with SHA-256 evidence performs one additional read under the same endpoint/tenant predicate. It examines at most 1,000 recent source records and one lookahead, with a 3-second database time limit. Only records inside the requested UTC window participate. A process GUID with conflicting observed image hashes is excluded. There is no PID, path, filename, or writer-to-file hash substitution.

Context returns at most 50 execution records and 100 network records per file observation, with explicit truncation and incomplete-scan indicators. It is available-record coverage, not a claim of complete network history. Source record IDs and timestamps remain visible and export with the observation.

Eight correlation tests pass (including authorized-predicate preservation and cursor closure): exact joins, PID rejection, different/missing hashes, conflicting GUID identities, UTC window validation, scan limits and result limits. Browser fixtures additionally check two-computer network destinations and ports. Live endpoint/backend validation is still pending.

## Concrete remaining service dependencies

- `backend/edr_plane/response.py` currently supports KILL_PROCESS, ISOLATE_ENDPOINT and RELEASE_ISOLATION. The wider response enum alone does not implement file retrieval, quarantine, deletion or application control. These require sensor execution, authorization, result handling and audit integration.
- `backend/edr_plane/file_content_acquisition.py` admits supplied acquisition hashes; it is not an on-demand file retrieval service.
- Crucible needs an operational submission/job/result service before a submission action can be enabled.
- Verified entry point, signed PE/certificate metadata and detection verdicts need explicit source evidence and ingestion mappings. Earliest observation, extension and absence of detections cannot substitute.

These gaps prevent claiming full Cisco functional parity. This follow-up changes only the EDR evidence service, EDR presentation, their tests and this document; it does not modify the XDR implementation or promote production.
