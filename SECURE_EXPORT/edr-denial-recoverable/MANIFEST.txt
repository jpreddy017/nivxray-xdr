NIVXFORGE EDR · "RECHECK ACCESS" PERMANENT REPAIR
=================================================
Frontend only. No authorization logic, policy, route permission or API
contract is touched. NOT related to, and NOT mixed with, the Windows
Gate 4 branch.

WHY THIS EXISTS
---------------
PR #17 fixed the CAUSE of the /edr loop: a 403 TENANT_REQUIRED ("pick a
customer") was being reinterpreted as "you are forbidden". This change
fixes the two properties that made that loop UNRECOVERABLE rather than
merely wrong, so a DIFFERENT refusal code can never reproduce it.

1 . THE LATCH IS IDEMPOTENT
    invalidateSecurity("denied", path) bumped the epoch on every call.
    Re-latching an ALREADY-latched denial for the SAME path therefore
    remounted the surface, which re-ran the read that had just been
    refused, which latched again - a render/request storm in which
    "Recheck access" appears to do nothing at all.
    The identical latch is now a no-op. Nothing is denied less: the
    first latch still stands, a denial for a DIFFERENT path still
    latches, and scope/session/expired/permission still invalidate.

2 . THE REFUSAL KEEPS ITS SHELL
    A latched route denial replaced the entire console with one sentence
    and one button. The customer pill, the product navigation and
    sign-out went with the page, so the ONE action that can change the
    server's answer - selecting a customer - was unreachable, and the
    button could only re-run the request that had just been refused.
    An /edr refusal now renders INSIDE NivXForgeConsole. The page body
    is still NOT loaded, the server is still the authority, and nothing
    is granted: the operator simply keeps the controls.

CHUNKING
--------
EdrAccessNotice stays a lazy /edr chunk. Importing NivXForgeConsole from
the router put the EDR console in the XDR ENTRY chunk (+10.2 kB gzip,
measured). Entry chunk is unchanged at 86.39 kB gzip; the notice is its
own 0.38 kB chunk. The Suspense fallback is the refusal ITSELF, so there
is no blank frame on the exact screen whose blankness is the defect.

ALSO
----
data-testid added to both recovery controls (route-recheck-access,
route-retry-authorization). Neither existed, so neither was drivable by
a test or by the testing agent.
