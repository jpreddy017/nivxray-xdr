THE DEFECT (measured, not read)
-------------------------------
EndpointRecord carries group_id, policy_id, placement_basis, placement_at,
deployment_id, policy_source, policy_assigned_at and policy_assigned_by and
defaults them all to None. store.enroll `$set` the whole record, so every
re-enrolment CLEARED them — and the enrolment route then saw an endpoint
with no group and assigned the DEFAULT group and policy. A recovered
computer silently left the group an administrator chose, and a stricter
policy was replaced by the default one.

Driving the live-equivalent code through REVOKED -> fresh token -> ACTIVE:
  group_preserved  : FALSE
  policy_preserved : FALSE
Everything else was already safe: same endpoint_id, one endpoint document,
ENROLLED/ACTIVE, sensor_state healed off REVOKED, event_count 157,226 and
every delivery field intact, new credential, old credential still REVOKED.

THE FIX
-------
1. backend/edr_plane/enrollment/store.py (+13)
   Placement and policy provenance join the delivery record in the
   INSERT-ONLY partition. A new endpoint is still placed at enrolment (the
   fields are inserted empty and the route's guarded update matches); an
   existing one keeps what it was given (the guard no longer matches).
2. backend/routers/edr_onboarding.py (+20/-2)
   assign_default_placement / assign_deployment_placement now return the
   EFFECTIVE placement instead of the INTENDED one. Both were already
   guarded on "has no group yet", so on a re-enrolment they returned a group
   the endpoint was not in — which the enrolment response reported to the
   agent as its placement.
No contract changes: the OpenAPI document is unaffected.
